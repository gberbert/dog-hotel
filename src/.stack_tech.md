# Documentação de Stack Tecnológica e Arquitetura

Este documento serve como referência técnica para a arquitetura, tecnologias e decisões de design do projeto **Dog Hotel**. O objetivo é facilitar a manutenção futura, onboarding de novos desenvolvedores e entendimento geral do sistema.

## 1. Visão Geral
O projeto é uma aplicação web moderna do tipo SPA (Single Page Application) focada no gerenciamento de um hotel para cães. A arquitetura é baseada em serviços **Serverless** utilizando o ecossistema **Firebase**, com um frontend reativo e performático.

## 2. Frontend (Client-Side)

A interface do usuário é construída com foco em componentização, performance e experiência do usuário (UX).

*   **Core Framework:** React 19
    *   Utiliza as mais recentes funcionalidades da biblioteca (Hooks, Functional Components).
*   **Build Tool & Dev Server:** Vite 
    *   Configurado para alta performance de desenvolvimento (HMR) e build otimizado.
    *   Utiliza `rolldown-vite` (conforme overrides).
*   **Linguagem:** JavaScript (ESModules / ESM)
*   **Estilização (CSS):** Tailwind CSS v3.4
    *   Utilização de utility-classes para desenvolvimento ágil.
    *   Processado via PostCSS (`autoprefixer`, `@tailwindcss/postcss`).
*   **UI Assets:**
    *   **Ícones:** `lucide-react` para uma biblioteca de ícones consistente e leve.
*   **Integração com Backend:** Firebase Web SDK v12.6
*   **Qualidade de Código:**
    *   **Linting:** ESLint v9 com plugins para React (`react-hooks`, `react-refresh`).

## 3. Backend (Serverless)

A lógica de negócio sensível e tarefas agendadas residem em funções serverless, garantindo escalabilidade e isolamento.

*   **Plataforma:** Cloud Functions for Firebase
*   **Estrutura:** Diretório `/functions` isolado.
*   **Runtime:** Node.js 20
*   **Linguagem:** JavaScript
*   **Dependências Principais:**
    *   `firebase-admin`: Para manipulação privilegiada do banco de dados e autenticação.
    *   `firebase-functions`: SDK para definição de triggers (HTTP, Firestore, Auth, etc).
    *   `date-fns` & `date-fns-tz`: Manipulação robusta de datas e fusos horários.
*   **Linting:** ESLint com `eslint-config-google` para padronização.

## 4. Banco de Dados e Armazenamento

*   **Database:** Cloud Firestore (NoSQL)
    *   Estrutura baseada em documentos e coleções.
    *   Configuração de regras de segurança em `firestore.rules`.
    *   Definição de índices compostos em `firestore.indexes.json`.

## 5. Infraestrutura e DevOps

*   **Hospedagem & Serviços:** Firebase
    *   **Functions:** Computação serverless.
    *   **Firestore:** Banco de dados.
*   **Configuração:** `firebase.json` (define configurações de functions e firestore).
*   **Scripts de Automação:**
    *   `release.js`: Script customizado para gerenciamento de releases.
    *   `gerar-contexto.cjs`: Utilitário para geração de contexto do projeto (provavelmente para IA ou documentação).
    *   `git-reset.js`: Script auxiliar para operações de git.
*   **Versionamento:** Git

## 6. Estrutura de Diretórios

*   `/src`: Código fonte da aplicação Frontend (Componentes, Páginas, Hooks, Utilitários).
*   `/functions`: Código fonte das Cloud Functions (Triggers, API).
*   `/public`: Arquivos estáticos servidos diretamente (ícones, manifesto, etc).
*   `/`: Arquivos de configuração na raiz (Vite, Tailwind, ESLint, Git, Firebase).

## 7. Arquitetura

O sistema adota uma arquitetura **Serverless Híbrida**, combinando acesso direto ao banco de dados pelo frontend (para operações CRUD de baixa latência) com lógica de backend centralizada para tarefas agendadas e notificações.

### 7.1. Fluxo de Dados e Padrões
*   **Frontend (Direct-to-Database):** Para a maioria das operações de leitura e escrita (Clientes, Reservas), o Frontend comunica-se diretamente com o Firestore utilizando o SDK Web. A segurança é garantida via `firestore.rules`.
*   **Backend (Eventos e Cron):** Lógica complexa que independe da interação do usuário ou precisa ser executada periodicamente reside nas Cloud Functions.
    *   **Exemplo Principal:** A função `checkScheduledAlerts` (Trigger HTTP) atua como um Job CRON. Ela varre o banco de dados em busca de eventos de check-in/out e horários de medicação, disparando notificações push (FCM) proativamente.

### 7.2. Detalhamento da Cloud Function (`checkScheduledAlerts`)
*   **Gatilho:** Requisição HTTP (Geralmente acionada por um agendador externo, ex: UptimeRobot/Cloud Scheduler).
*   **Responsabilidades:**
    1.  **Sincronia Temporal:** Opera forçosamente no fuso horário 'America/Sao_Paulo'.
    2.  **Briefing Diário:** Identifica entradas e saídas do dia.
    3.  **Medicação:** Verifica horários exatos para lembretes de remédios.
    4.  **Push Notifications:** Envia alertas via Firebase Cloud Messaging (FCM) para dispositivos registrados e realiza a limpeza automática de tokens inválidos.

### 7.3. Estrutura de Dados (Firestore)
Os dados principais residem sob um caminho raiz de tenant/app:
`artifacts/{appId}/public/data`
*   `/clients`: Coleção de clientes e seus dados (incluindo sub-arrays de medicação).
*   `/bookings`: Coleção de reservas com datas de check-in/out.
*   `/notifications`: Inbox de mensagens geradas pelo sistema.
